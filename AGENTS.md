# AGENTS

This repository follows the guidance from [Rust Best Practices](https://github.com/apollographql/rust-best-practices)
(Apollo GraphQL Rust Best Practices Handbook). `google-genai-rs` is a Rust port of the
[Google Gen AI Python SDK](https://github.com/googleapis/python-genai) for the Gemini
Developer API. See `specs/001-port-genai-rust/` for the full spec/plan/tasks.

## Scope

- Applies to all Rust files matching `**/*.rs`.
- Focus on correctness, intent clarity, and maintainability first, with performance changes based on evidence.

## Generated code — do not hand-edit

The following are produced by `tools/codegen/*.py` from the Python SDK and MUST NOT be
edited by hand. Change the generator or its override files instead, then re-run
`python tools/codegen/generate.py`:

- `src/types/generated/`
- `src/converters/generated/`
- `src/blocking/generated.rs`
- `tests/fixtures/converters/**`
- `docs/parity.md`

Files each start with `// @generated by tools/codegen/<script>.py from google-genai <version>. DO NOT EDIT.`

## Core rules

- Never "clean up", replace, or normalize in-progress user experiments unless explicitly asked.
- Never modify git history.
- Favor simplicity. Write the least complex code that solves the problem — clarity beats cleverness.
  - Prefer simple code over elegant code; prefer elegant code over complex code.
- Rust style should follow a functional-first approach (immutability, pure helpers, composition over shared mutable state).
- Keep transform chains readable and line-broken.
- Always check `git status --short --branch` before starting work.
- Minimum Rust quality gates (must remain covered or be run explicitly):
  - `cargo fmt --all --check`
  - `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings`
  - `cargo test --workspace --all-features`
  - `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features`
  - `python tools/codegen/generate.py && git diff --exit-code` (generated code is in sync)
- Avoid magic strings. Extract string literals used as identifiers or keys into named constants.
- Never log API keys, request bodies, or response bodies containing user content — see `src/http/headers.rs`.

## Core Rust coding rules

- Default to borrowing (`&T` / `&mut T`) and avoid cloning unless ownership is required.
- Prefer small `Copy` types by value; pass heap-backed or large types by reference.
- Use explicit ownership in public APIs (`&str` / `&[T]` preferred over owned inputs unless needed).
- Prefer `?` for fallible flow and use `let PATTERN = EXPR else { ... }` or
  `if let ... else` for structured early-exit patterns.
- Prefer `if`/`else if`/`else` over `if` with early `return`.
- Use `_or_else` / lazy defaults and avoid eager allocation when not needed.
- Prefer iterator pipelines for pure transformations; use `for` loops when break/continue/early return or complex side effects are required.
- Keep import groups ordered: `std/core/alloc`, external crates, workspace, `super::`, `crate::` (see `rustfmt.toml`).
- Prefer references before pointers; use `Arc`/`Rc` only when ownership model requires it.
- Prefer `From`/`Into` trait conversions over manual bit-transform conversion implementations.
- Keep side effects at system boundaries (HTTP/WebSocket I/O), and keep transformation logic (`converters`, `transformers`) side-effect free.

## Error and API quality

- This is a library crate: use typed errors (`thiserror`), never `anyhow`.
- Avoid silent recovery from `Err`; keep root-cause visibility (`tracing::debug!`/`inspect_err`).
- Public items must be documented with `///`, including `# Errors` / `# Panics` / `# Examples` where applicable (`missing_docs = "deny"`).
- Keep comments purposeful (`why`, assumptions, constraints, safety); remove stale comments.
- Convert TODOs to issue-linked notes like `// TODO(issue #NNN): ...`.

## Panic/Unwrap Policy

- `clippy::unwrap_used` and `clippy::expect_used` are `deny` at the crate level (see `Cargo.toml` `[lints.clippy]`).
- `unwrap`/`expect` are allowed only in `#[cfg(test)]` code (`clippy.toml`: `allow-unwrap-in-tests`/`allow-expect-in-tests`).
- Runtime fallible paths must return `Result` with a typed `Error` variant instead of panicking.

## Testing and review

- One behavior per test, with descriptive names (`mod` per unit under test).
- Cover success and error behavior for behavioral paths.
- Unit tests for internals (`#[cfg(test)]` in the same file), integration tests for public behavior (`tests/`).
- Use `insta` snapshot tests only for complex, stable structured outputs; prefer `assert_eq!` for primitives/small structs.
- Avoid unnecessary `#[allow]`; prefer explicit local `#[expect(clippy::lint, reason = "...")]` only when justified.
- High-risk review triggers: unnecessary cloning in hot paths, unjustified `#[allow]`, missing error context, TODOs without an issue reference.

## Dispatch strategy

- Prefer static dispatch (`impl Trait` / generic bounds) when types are known and performance matters.
- Use dynamic dispatch (`dyn Trait`) for plugin-style/runtime polymorphism (e.g. `FunctionTool`, MCP tools).
- Delay boxing until required by design boundaries.
