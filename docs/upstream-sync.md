# Upstream sync status

Hand-maintained (unlike `parity.md`, this is not generated — update it by
hand whenever the upstream pin changes). Answers three questions a future
maintainer will have: "what upstream state are we pinned to?", "where does each
upstream module live in this crate?" and "how do I take the next upstream
release without re-reading the whole SDK?"

The short answer to the third: run `sync_diff.py`, port only the entries it
lists, and let `check_ledger.py` and `check_upstream_tests.py` tell you what
is still missing.

## Module map

One Rust file (or directory) per upstream module. The leading `_` of a private
upstream module is dropped, Rust names are the `snake_case` / `PascalCase` of
the upstream names, and definition order follows upstream so that a reordering
upstream is visible in a diff. `tools/codegen/module_map.toml` encodes this
table and the ledger check reads it.

| Upstream (`google/genai/…`) | Rust | Notes |
|---|---|---|
| `__init__.py`, `version.py` | `src/lib.rs` | The version is `env!("CARGO_PKG_VERSION")` |

## Reading the symbol ledger

`tools/codegen/ledger.toml` has one `[[symbol]]` for every top-level function,
class, method and constant of the pinned upstream package, in upstream's
definition order. Private symbols are included, because a changed private
helper changes behavior too.

| Field | Meaning |
|---|---|
| `module`, `qualname`, `kind` | Where the symbol is upstream (`function`, `class`, `method` or `const`) |
| `public` | `false` for a `_`-prefixed module or name, or a name missing from an existing `__all__` |
| `fingerprint` | Hash of the symbol's `ast.unparse` text, so a change to a comment, docstring, formatting or import order does not change it |
| `status` | `ported`, `generated`, `merged` (folded into a public sibling), `out_of_scope` or `unmapped` |
| `rust` | The Rust item, as `path::item`, for every status except `out_of_scope` |
| `reason_code`, `reason` | Required for `out_of_scope`; one of `vertex`, `python_only`, `replay_infra`, `structural`, `not_applicable` |

The Rust counterpart is derived by the naming rule above and corrected by
`tools/codegen/deviations.toml`, where each exception is `renamed`, `merged`,
`not_ported` or `generated` and carries a reason.

- `check_ledger.py` fails when the checked-in file differs from what the
  installed SDK produces, and when any symbol is `unmapped`. CI runs it.
- To accept a symbol that has no obvious counterpart, add a `deviations.toml`
  entry (or fix `module_map.toml`) and run `generate.py --only ledger`. Do not
  edit `ledger.toml` by hand.

## Reading the test inventory

`tools/codegen/upstream_tests.toml` lists every upstream test, and every item of
a table-driven test, with one of three statuses.

| Status | Meaning | Fields |
|---|---|---|
| `mapped` | Ported to a Rust test, or replayed from the oracle corpus | `rust` names the test; for a table case it is `tests/fixtures/upstream/<dir>/<stem>.json::<case>` |
| `excluded` | Deliberately not ported | `reason_code` and `reason`; the codes are `vertex`, `python_only`, `replay_infra`, `live_network`, `pydantic_only` and `duplicate_of` |
| `pending` | Not yet decided | Allowed while syncing; the final gate rejects it |

Layout: `google/genai/tests/<dir>/test_<stem>.py` becomes
`tests/<dir>/<stem>.rs`, declared in `tests/<dir>/main.rs`. A ported test keeps
its upstream name and carries a marker right above it:

```rust
// upstream-test: models/test_generate_content.py::test_http_options_in_generate_content
#[tokio::test]
async fn test_http_options_in_generate_content() { … }
```

`check_upstream_tests.py` fails on a test that is new or gone upstream, on a
`mapped` entry whose marker is missing, on an `excluded` entry without a valid
reason, and (with `--final`) on any `pending` entry. `--list` shows the pending
ones and `--report` prints the counts per status and per reason code.

### The oracle corpus

Upstream's table-driven tests run against recorded replays that are not
published. `gen_upstream_cases.py` runs each in-scope case once against the real
Python SDK with a capturing HTTP transport and stores the request it produced in
`tests/fixtures/upstream/`. `tests/upstream_table/` replays the same parameters
through this crate and compares method, path, query and JSON body. A failure is
named `<upstream file>::<case>`, so a divergence points at its origin and the
expected value is whatever Python actually sends rather than a hand-written
guess. The corpus files are generated; change the generator, not the JSON.

## Syncing to a new upstream version

Set `OLD` to the current pin and `NEW` to the release you are taking. All
commands use the codegen venv from [CONTRIBUTING.md](../CONTRIBUTING.md#generated-code).

1. **Diff against the old version.** `python tools/codegen/sync_diff.py --from
   $OLD --to $NEW`. It lists only symbols whose fingerprint changed, plus added
   and removed ones, each with its Rust counterpart, ledger status and a diff
   limited to that symbol. A trailing line gives the counts
   (`changed=… added=… removed=… unmapped=…`); `--format json` gives the same
   data in a stable shape.
2. **Bump the pin.** Edit `PINNED_VERSION` in `tools/codegen/upstream.py` and the
   `google-genai==` pin in `tools/codegen/requirements.in`, relock with
   `uv pip compile tools/codegen/requirements.in --generate-hashes
   --python-version 3.12 -o tools/codegen/requirements.txt`, and reinstall the
   venv.
3. **Regenerate.** `python tools/codegen/generate.py` regenerates the types,
   converters, fixtures, oracle corpus, gaos modules, blocking wrappers, parity
   document and ledger.
4. **Port the hand-written items.** For each `changed` or `added` entry the
   report named, change the Rust item it points at. Private symbols that a
   listed public symbol calls are not linked automatically; they appear as their
   own entries.
5. **Check.** Run `check_upstream_tests.py`: new or changed upstream tests show
   up as `pending`, so map each to a Rust test or exclude it with a reason, and
   finish with `check_upstream_tests.py --final`. Then `check_ledger.py`, which
   fails on any `unmapped` symbol, and the Rust gates in CONTRIBUTING.md.
6. **Record it.** Update the table in [Current pin](#current-pin), add the
   CHANGELOG entry, and move anything deliberately left behind into
   [Known gaps](#known-gaps) or [Deliberately deferred](#deliberately-deferred).

To prove the oracle corpus has teeth, change one branch of `t_part` in
`src/transformers.rs` and run `cargo test`: it fails with a message naming an
`upstream-test:` marker or a corpus case. Revert afterwards.

## Known gaps

Behavior this crate has today that differs from upstream 2.28.0 and is not a
documented design choice. Fix them when you are next in the area; none blocks a
release.

| Area | Gap | Effect |
|---|---|---|
| `interactions` | `CreateInteractionRequestBody` is an untagged union whose two variants are both all-optional | Deserializing `{"model": …, "input": …}` yields the agent variant. Serialization is unaffected |
| `interactions` | The derived `output_text` and `output_image` properties are not implemented | Read the output items directly |
| `interactions` | `stream: true` inside the `create()` body is not implemented | Use the streaming method |
| `environments` | The upload MIME type is guessed with `mime_guess` | `.py` is `text/plain`; Python says `text/x-python` |

Deviations that are deliberate (for example `Chats::create` keeping unknown
roles as user turns, MCP schemas passed through as `parameters_json_schema`)
live in `tools/codegen/deviations.toml` with a reason each, and the user-visible
ones are listed in
[Known divergences](migrating-from-python.md#known-divergences-from-the-python-sdk).

## Permanently out of scope

Not "not yet" — deliberately not ported, with the decision that settled it.

| Area | Why | Decided in |
|---|---|---|
| Vertex AI backend | This crate targets the Gemini Developer API only; asking for Vertex AI (`vertexai(true)`, `project`/`location`, `GOOGLE_GENAI_USE_VERTEXAI`) fails fast with `Error::UnsupportedBackend`. Vertex-only upstream symbols and tests carry the reason code `vertex` | 001 |
| `local_tokenizer` | Needs a sentencepiece model download and makes no API request | 001 |
| `_replay_api_client`, `_test_api_client` | Upstream's own test-replay harness; this crate proves parity through golden fixtures and the oracle corpus instead | 003, 008 |

"Permanent" isn't immutable. If one of these becomes in-scope, move its row to
[Current pin](#current-pin) with a note explaining the change instead of
deleting it. The Interactions API and the `_gaos` sub-SDK were in this table
until 0.4.0, which ported them.

## Future work

- **Method skeletons for the classic resources.** `models.rs`, `batches.rs` and
  the other hand-written resource modules are ported by hand. Generating their
  method skeletons from the upstream AST would remove that step, but it is a
  larger, separate effort. Until then the oracle corpus and the ledger make a
  change to their orchestration visible and executable, so the risk is
  contained.
